## 2. Problem Statement

ADAS vision reviewer는 GT 없이 많은 visualizer output을 봐야 한다. 사람은 보통 다음 과정을 머릿속으로 한다.

```text
1. 이 frame의 실제 장면을 본다.
2. overlay가 무엇을 그리고 있는지 본다.
3. JSON 값이 overlay/장면과 맞는지 본다.
4. 앞뒤 frame에서 튀는지 본다.
5. OD/LD/RBD/TS/TL 같은 feature 기준으로 수상한 현상을 분류한다.
6. 사람이 더 봐야 할지 정한다.
```

이 제품은 이 과정을 자동화한다. 정확히 말하면 최종 결정을 자동화하는 것이 아니라, **frame evidence를 기반으로 1차 tester review를 자동화**한다.

제품의 핵심 질문은 이것이다.

```text
"이 frame/context에 대해 VLM tester가 볼 수 있는 모든 근거를 모아줬을 때,
 사람이 놓치기 쉬운 suspicious candidate를 빠르게 찾을 수 있는가?"
```

## 4. The Product Shape

이 제품은 다음 2단계 모델로 보는 것이 가장 명확하다.

```text
Stage A. Case to Evidence
  여러 입력 방식에서 평가할 frame 후보를 만들고,
  VLM이 볼 수 있는 evidence package로 변환한다.

Stage B. Evidence to Judgment
  frame evidence package를 보고 VLM tester가 정성 평가한다.
```

이때 `Normalized Evaluation Case`와 `Frame Evidence Package`는 같은 것이 아니다.

```text
Normalized Evaluation Case
  아직 "무엇을 평가할지"에 가까운 주문서다.

  예:
    case_id
    video_path
    json_dir
    frame_list
    start_frame/end_frame
    sample_count
    project_type
    focus_feature
    frame_metadata

Frame Evidence Package
  실제 VLM이 평가할 한 frame/context 단위 입력이다.

  예:
    case_id
    sampled_frame
    center frame image
    context image/strip
    JSON snippet
    JSON summary
    frame metadata
    video metadata
    project_type
    focus_feature
```

이 구분이 중요하다.

```text
Evaluation Case는 adapter의 출력이다.
Frame Evidence Package는 evidence builder의 출력이다.
VLM Tester는 Evaluation Case가 아니라 Frame Evidence Package를 평가해야 한다.
```

### 5.1 Issue-Centric 전제를 제거한 점

`issue_hint`, `target_id`, `Jira` 전제를 제거한 것은 맞다. 이 도구의 입력 계약은 이제 `frame evidence package`다. 이게 제품을 단순하게 만든다.

```text
좋은 점
  - VLM이 특정 claim에 끌려가지 않는다.
  - frame 전체를 tester처럼 본다.
  - 입력 방식이 바뀌어도 core 판단은 유지된다.
```

### 5.2 Adapter와 Core Engine 분리

현재 요구사항의 가장 중요한 설계 결정이다.

```text
Excel adapter
JSON manifest adapter
CLI adapter
folder scan adapter
external workflow adapter
        ↓

```

이 구조를 지켜야 나중에 입력 방식이 늘어나도 제품이 무너지지 않는다.

### 5.3 VLM Guardrail이 현실적임

VLM이 final authority가 아니라는 점, GT accuracy를 claim하지 않는 점, sync/visualizer ambiguity를 분리하는 점은 좋다.

이 제품에서 가장 위험한 실패는 다음이다.

```text
VLM이 그럴듯하게 "SW issue입니다"라고 단정하는 것
```

현재 요구사항은 이 위험을 꽤 잘 막고 있다.

### 5.4 `observed_evidence / inference / uncertainty` 분리

이건 반드시 유지해야 한다.

```text
observed_evidence
  영상/overlay/JSON에서 실제 확인한 것

inference
  그 근거로 추론한 것

uncertainty
  판단을 약하게 만드는 조건
```

이 구분이 있어야 VLM report가 tester review로 쓸 수 있다.

## 6. Main Concerns

### Concern 1. Frame Evidence Package가 아직 정식 schema로 분리되어 있지 않다

현재 요구사항에는 `Normalized Evaluation Case` schema는 있다. 하지만 VLM이 실제로 받는 `Frame Evidence Package` schema는 `VLM Input`과 output folder 구조에 흩어져 있다.

이건 구현자가 헷갈릴 수 있다.

```text
헷갈릴 수 있는 구현
  VLM prompt가 Evaluation Case를 직접 먹음
  -> 아직 frame image/context/JSON summary가 없는 상태라 평가 품질이 흔들림

좋은 구현
  Evaluation Case
    -> sampled frames
    -> evidence artifacts
    -> Frame Evidence Package
    -> VLM Tester
```

권장 보강:

```text
Frame Evidence Package Schema 섹션을 별도로 추가한다.
```

예:

```text
Frame Evidence Package required fields:
  case_id
  sampled_frame
  timestamp_sec
  center_frame_image
  context_image
  video_metadata
  project_type

Recommended fields:
  json_snippet
  json_summary
  frame_metadata
  focus_feature
  evidence_integrity
  source_case_metadata
```

### Concern 2. `regression_feature_issue_type_definitions_en.md`는 issue-centric 문서다

현재 reference로 남아 있는 `regression_feature_issue_type_definitions_en.md`는 유용하다. 하지만 문서 자체는 기존 regression issue/rule vocabulary를 설명한다.

즉 VLM에게 이 문서를 그대로 주면 다음 위험이 있다.

```text
위험
  VLM이 frame을 보기도 전에 issue type taxonomy 중심으로 생각한다.

원하는 동작
  frame evidence를 먼저 보고,
  필요할 때만 feature/suspicious type label을 붙인다.
```

따라서 요구사항에 이 사용 원칙을 명시하면 좋다.

```text
regression_feature_issue_type_definitions_en.md usage policy:
  - It is a classification vocabulary.
  - It is not an input contract.
  - It must not cause issue-first evaluation.
  - VLM should use it only after describing observed frame evidence.
```

### Concern 3. `focus_feature`가 issue_hint처럼 오해될 수 있다

`focus_feature`는 남겨두는 게 맞다. 하지만 구현자가 이것을 너무 강하게 쓰면 문제가 된다.

```text
잘못된 사용
  focus_feature = OD
  -> OD만 보고 lane/light/sign 문제는 무시

좋은 사용
  focus_feature = OD
  -> OD를 먼저 보되, frame에서 명확한 다른 feature 이상이 보이면 같이 기록
```

요구사항에는 이미 "first review lens but still evaluate broadly"가 들어 있다. 좋다. 이 문구는 유지해야 한다.

### Concern 4. Phase 1에 "Evidence Builder" 이름이 필요하다

현재 Phase 1은 sampling/evidence report다. 맞다. 다만 최신 전제에서는 Phase 1의 핵심 산출물이 더 명확하다.

```text
Phase 1 output:
  Frame Evidence Package
```

즉 Phase 1은 단순히 image 저장이 아니라, VLM이 나중에 먹을 수 있는 표준 evidence unit을 만드는 단계다.

요구사항에 이 이름을 넣으면 구현 방향이 좋아진다.

### Concern 5. `frame_metadata`는 자유도가 높지만, 사용 정책이 필요하다

`frame_metadata`는 좋다. 다양한 입력 방식에서 풍부한 정보를 전달할 수 있다.

다만 이 metadata가 VLM 판단을 오염시키면 안 된다.

권장 정책:

```text
frame_metadata can include:
  - source campaign
  - SW version
  - project variant
  - weather/road/test group label
  - external batch id

frame_metadata should not be treated as:
  - ground truth
  - defect claim
  - expected answer
```
